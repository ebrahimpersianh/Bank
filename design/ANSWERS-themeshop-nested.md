# جوابِ دو سوالِ بازِ `18b` و `36b`

## ۱ · `AppPrimary` — ✅ سوالِ بلوکه‌کننده منتفی است، **از قبل انجام شده**

`AppPrimary` همین حالا دقیقاً همان شکلی است که پیشنهاد دادی:

```kotlin
// ui/theme/Color.kt خطِ ۳۴۳
val AppPrimary: Color @Composable get() = LocalAppColors.current.primary
```

یعنی مهاجرتِ پرریسکی که نگرانش بودی ماه‌ها پیش انجام شده. تفاوتِ اسم: `LocalAppColors`
است نه `LocalPalette`، و کلاسِ پالت `AppColorPalette` نام دارد.

**سه توکنِ مشتقی که خواسته بودی هم از قبل هستند** — و همان‌طور که حدس زده بودی
`AppPrimaryInk` با آلفا ساخته نشده، فیلدِ مستقلِ خودش را دارد:

```kotlin
val AppPrimaryPill: Color   @Composable get() = LocalAppColors.current.primaryPill
val AppPrimaryBorder: Color @Composable get() = LocalAppColors.current.primaryBorder
val AppPrimaryInk: Color    @Composable get() = LocalAppColors.current.primaryInk
val AppPrimaryDim, AppPrimaryInkLight, AppPrimaryPillBorder  // این‌ها هم هستند
```

**جوابِ «چند مورد بیرونِ `@Composable` است؟»: صفر.**

گرداندنِ `AppPrimary` در کلِ پروژه ۱۹۹ استفاده می‌دهد و **همه داخلِ تابعِ `@Composable`
هستند**. آن‌هایی که به شکلِ `val x = AppPrimary` دیده می‌شوند استثنا نیستند، بلکه **قاعده‌ی
ثبت‌شده‌ی پروژه‌اند**: توکن‌های رنگ `@Composable`اند و داخلِ بلوکِ `Canvas`/`DrawScope`
صدا زده نمی‌شوند، پس **قبل از `Canvas` در یک `val` محلی خوانده می‌شوند**. مثال:

```kotlin
val arc = AppPrimary          // ← داخلِ @Composable، درست بالای Canvas
Canvas(...) { drawArc(color = arc, ...) }
```

**پس بدونِ نگرانی جلو برو**: نه به `MaterialTheme` نیازی هست، نه به راهِ کم‌ریسکِ جایگزین.
هر توکنِ تازه‌ای که برای تمِ رنگی لازم داری، یک فیلد به `AppColorPalette` اضافه می‌شود و
یک `val ... @Composable get()` کنارِ بقیه — کارِ ما، تو فقط مقدارها را بده.

⚠️ یک قاعده‌ی پروژه که به کارت می‌آید: `line` و `glass*` از `primary` مشتق می‌شوند، پس
**هر پالتِ تازه باید این‌ها را هم‌قدم به‌روز کند** وگرنه حاشیه‌ی کارت‌ها با تمِ تازه
ناهماهنگ می‌شود. یک بررسیِ ایستا (`palette.py`) هست که فیلدِ ناموجود را قبل از بیلد می‌گیرد.

## ۲ · حذفِ دسته‌ی مادرِ زیرمجموعه‌دار — **گزینه‌ی ۲ (ترفیعِ زیرمجموعه‌ها)**، با یک قید

پیشنهادِ خودت درست است، و **با رفتاری که برنامه از قبل دارد هم‌خانواده است**: امروز
حذفِ دسته‌ای که تراکنش دارد، تراکنش‌ها را بی‌صدا یتیم نمی‌کند — از کاربر می‌پرسد به کدام
دسته منتقل شوند. همان اصل اینجا هم صدق می‌کند: **هیچ داده‌ای بی‌سوال از بین نرود.**

پس:
- زیرمجموعه‌ها **به مادر ترفیع می‌گیرند** (سطحِ اول می‌شوند)، حذف نمی‌شوند.
- اگر خودِ مادر **تراکنش** هم داشته باشد، همان دیالوگِ موجودِ «به کدام دسته منتقل شود؟»
  سرِ جایش می‌ماند — دو پرسش پشتِ‌هم نه؛ یک دیالوگ که هر دو را می‌گوید.
- متنِ تایید باید صریح بگوید چند زیرمجموعه ترفیع می‌گیرند، وگرنه کاربر فکر می‌کند
  کلِ شاخه پاک شده.

فریمِ این دیالوگ را لطفاً بده — و اگر ممکن است هم‌شکل با فریمِ **تاییدِ کنشِ سراسری**ی
بندِ ۲ِ `MESSAGE-round6-to-design.md` باشد، تا برنامه یک زبانِ تایید داشته باشد نه دو تا.

**قیدِ مدلِ داده** (تاییدِ حرفِ خودت که «محدودیت در مدل نه UI»): `CustomCategoryEntity`
فیلدِ `parentName` دارد — **نام**، نه id، چون مادر می‌تواند یک دسته‌ی **ثابت** باشد که اصلاً
ردیفِ دیتابیس ندارد. پس عمقِ دو تضمینِ ساختاری نیست و باید در همان لایه‌ی افزودن/ویرایش
جلویش گرفته شود؛ درست همان‌طور که نوشتی.
