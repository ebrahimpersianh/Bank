## اول: یک تصحیحِ README

بندِ ۲ات می‌گوید پسوندِ «ریال» قاعده‌ی قفل‌شده است. **در این فایل «تومان» است** و درست
هم همین است — بسته‌ی وام همه‌ی فیلدها را تومان کرد و بازه‌ها ÷۱۰ شدند. آن بند کهنه است؛
اگر جایی از README دیگری هم آمده، اصلاحش کن وگرنه دورِ بعد کسی برمی‌گرداندش به ریال.

## ۱ — 🚨 چهارمین موردِ باگِ `return`

```kotlin
if (showCalendarPicker) {
    CalendarPickerScreen(...)
    return
}
```

همان الگویی که در `AssetTradeSheet` و `AccountDetailScreen` رفع شد: `return` کلِ فرم را
از کامپوزیشن برمی‌دارد، پس اسکرول صفر می‌شود و کاربر بعدِ انتخابِ تاریخ خودش را بالای
فرم پیدا می‌کند. حالا `ModalBottomSheet` روی فرم می‌آید و فرم زنده می‌مانَد.

`skipPartiallyExpanded = true` چون تقویم تمام‌صفحه است — همان تصمیمی که در `AssetTradeSheet`
گرفتیم.

## ۲ — کارتِ خلاصه‌ی زنده

**بزرگ‌ترین گپِ فرم:** پنج عدد می‌پرسد و هیچ‌وقت نمی‌گوید جمعشان چقدر است. کاربری که
یک‌بار ۱۱ قسط به‌جای ۱۰ ثبت کرد، تا لحظه‌ی ذخیره راهی برای دیدنِ نتیجه نداشت — و بعدش
هم راهی برای اصلاح نبود، که کلِ حالتِ ویرایش از همان درخواست آمد.

کارت **بالای فرم** است نه پایین: اگر پایین باشد، کاربری که فیلدها را پر می‌کند
نمی‌بیندش و کلِ فایده‌اش همین دیدنِ زنده است.

و **تا وقتی قسط و تعداد نیامده کارت نمی‌آید** — نه این‌که «—» نشان بدهد. جایش یک خطِ
راهنما. کارتِ خالی یک ردیفِ مُرده است.

آخرین سررسید = سررسیدِ اول + (n−۱) ماه. وامِ دستی تنفس ندارد (`graceMonths` همیشه ۰)،
پس بی‌قید درست است.

## ۳ — سقفِ «تعدادِ کل» بالای فرم

گاردِ `n < editingLoan.paidCount` از قبل بود، ولی کاربر فقط وقتی می‌دیدش که اشتباه کرده
باشد — و آن‌وقت هم نمی‌دانست عددِ مجاز چند است. حالا نوارِ طلایی بالای فرم می‌گوید «۴
قسط پرداخت شده، کمتر از ۴ نمی‌شود». خطای بعدِ ذخیره سرِ جایش می‌مانَد به‌عنوانِ تورِ دوم.

## ۴ — سه کارت جای شش

فیلدها سه گروه‌اند: **شناسه** (اسم، بانک) · **عدد** (قسط، تعداد، تاریخ) · **وضعیت**
(پرداخت‌شده). شش کارتِ تک‌فیلدی یعنی شش سرصفحه و پنج فاصله‌ی بزرگ برای فرمی که در یک
صفحه جا می‌شد.

با یکی‌شدنِ کارت‌ها `AppCard(label = …)` کافی نیست، پس `FieldLabel` اضافه شد.

## ۵ — انتخابگرِ تاریخ: چرخ‌دنده حذف می‌شود

**دو نما، نه سه.** `InlineJalaliDateRow` برای تغییرِ کوچک (درجا، بی خروج از فرم) و
`CalendarPickerScreen` برای انتخابِ آگاهانه. چرخِ سه‌ستونه تنها جای اپ است که آن شکلی
است و همان کاری را می‌کند که ردیفِ درجا ارزان‌تر انجام می‌دهد — سه نما یعنی سه عادت.

خبرِ خوب: هر دو نمای باقی‌مانده **از قبل در این فایل هستند**، پس `29i` کارِ تازه‌ای
نمی‌خواهد جز حذف. اگر چرخ جای دیگری هم استفاده می‌شود، فهرستش را بده.

## دو چیز که باید تایید کنی

**۱. `AppHeroCard` و جوهرش.** فرض کردم `AppHeroCard { }` محتوا می‌گیرد (همان که
`AccountsTotalHero` استفاده می‌کند). دو رنگِ جوهر را تهِ فایل تعریف کردم، و این هگزِ
هاردکدِ نگران‌کننده نیست: گرادیانِ هیرو در هر دو تم سبزِ برند است نه توکنِ چرخنده، پس
سفید رویش همیشه درست است. ولی اگر `AppHeroCard` توکنِ جوهرِ خودش را دارد، آن دو را حذف
کن.

**۲. `AppGoldPill` / `AppGoldInk` / `AppLabel`.** در این فایل ایمپورت نبودند ولی جاهای
دیگرِ پروژه هستند. اگر نه: `AppGoldPill` → `AppGoldPillSoft`، `AppLabel` → `AppMuted`.

## پنج فایلِ دیگرِ مسیر

این دور فقط فرمِ افزودن را زدم — همان صفحه‌ی اسکرین‌شات و پردیده‌ترین. برای بقیه:

`CalculatorHostScreen` و `BankLoanScreen` و `ResultScreen` و `AffordScreen` و
`DepositScreen` را در بسته‌ی وام (دورِ قبل) از نظرِ **واحد و `Locale.US` و ارقام** اصلاح
کردم و آن اصلاحات اعمال شده‌اند. آنچه مانده **قابِ بصری** است: همان سه الگوی این فایل
(هیروِ خلاصه، گروه‌بندیِ فیلدها، شیت جای `return`) روی آن پنج تا هم می‌نشیند.

بگو کدام را اول می‌خواهی — `ResultScreen` بیشترین اثر را دارد چون خروجیِ هر سه
محاسبه‌گر است.
